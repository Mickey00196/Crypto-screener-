# FINDINGS

This is the escape-hatch document the build brief requires when a session
cannot produce a strategy that clears the Definition of Done on real data.
It applies here for a specific, narrow, and fully-diagnosed reason: **this
session's sandbox cannot reach any exchange API**, so Phase 1's real data
fetch never happened. Everything downstream of that (the real 50-config
optimization sweep, walk-forward validation, the one-shot holdout
evaluation, and live paper trading) is consequently unexecuted on real data
too. This is a well-documented, legitimate negative result about *this
session's environment*, not a finding about the strategies' quality — that
question is still open.

## What was actually verified this session

Everything in `bot/` was built and is real, tested code — 170 automated
tests, all passing, `ruff check .` clean:

| Phase | What was built | Tests |
|---|---|---|
| 0 — Research | `RESEARCH.md`: 8 strategy families surveyed with citations, indicator evidence table, 3 families selected | — |
| 1 — Data | ccxt fetchers for Binance/Bitvavo + a CoinGecko REST fetcher (real logic, mocked-HTTP tested), validation, chronological splitting, Parquet storage, synthetic-data generator | 35 |
| 2 — Engine | Event-driven bar-by-bar backtester: fees, slippage, stop/take-profit, multi-symbol portfolio, full trade log | 20 |
| 2b — Indicators | 30+ hand-tested indicators across 7 categories, including the Wilder-vs-simple-smoothing correctness the brief specifically warns about | 43 |
| 3 — Strategy/risk | Strategy protocol, 3 chosen strategies, a standalone-tested risk module (ATR sizing, daily loss limit, drawdown kill switch) | 9 + 10 |
| 4 — Optimization | Seeded config sampler, train/val aggregation, walk-forward + purged k-fold, Definition-of-Done gate checks, holdout guard | 25 |
| 5 — Live | Paper broker (simulated fills), gated live broker, restart-safe state, the trading loop's bar-processing logic | 18 |
| 6 — Dashboard | Streamlit app (headless-tested via `AppTest`), Docker, CI | 8 |

The **holdout guard was proven from both directions**: a rogue caller
(`tests/fixtures/rogue_caller.py`) is rejected with `HoldoutBreachError`,
and `evaluation/final_evaluation.py` — the one legitimate caller — succeeds.
The **lookahead detector was proven from both directions** too: a clean
strategy passes, and a deliberately-broken one (`shift(-1)`) is caught, with
the exact bar index reported.

`scripts/run_pipeline_smoketest.py` ran the full
`data → engine → optimizer → walk-forward → gates` pipeline end to end on
**synthetic** data (GBM + injected regimes — `data/synthetic.py`), tagged
`[SYNTHETIC SMOKE TEST]` everywhere it appears (`EXPERIMENTS.md`). It
proved the machinery runs correctly: configs get sampled, backtested,
logged, checked for overfitting, and walk-forward windows get evaluated.
The results were exactly what an honest small-sample run should look like —
mostly `OVERFIT_REJECTED` verdicts, a couple of `CANDIDATE`s that then
failed the trade-count and walk-forward-consistency gates on ~3,200 bars of
data. Nothing was tuned to make a gate pass. **These numbers are not, and
must never be read as, evidence about real strategy performance** — see the
tag on every row.

## The network blocker (why Phase 1 didn't run for real)

Confirmed directly, twice — once during planning, once independently
verified in the implementation session via `curl` and the proxy's own
status log:

```
gateway answered 403 to CONNECT (policy denial or upstream failure)
host: api.binance.com:443
host: api.bitvavo.com:443
```

Even an unrelated host (`google.com`) is blocked the same way — this
sandbox's egress is allowlisted to `pypi.org`, `files.pythonhosted.org`,
`registry.npmjs.org`, and a handful of other package/dev hosts, nothing
else. `pip install` works; live HTTP calls to any exchange do not.

This is why:
- `data/fetch_binance.py` / `data/fetch_bitvavo.py` have never been run
  against a live exchange in this session — only against a mocked exchange
  object in `tests/test_data/test_fetch.py`.
- `config/holdout.yaml` does not exist (see `config/holdout.yaml.template`)
  — it's generated by `data/splits.py` from real fetched data, which
  doesn't exist yet.
- `scripts/run_optimization.py` (the real 50-config-per-family sweep) has
  never been run — it depends on `config/holdout.yaml` and real Parquet
  data existing.
- `evaluation/final_evaluation.py` has never been run against real holdout
  data — only against synthetic data in
  `tests/test_evaluation/test_final_evaluation.py`, which exists purely to
  prove the holdout guard's legitimate-caller path works.
- The paper-trading loop (`live/trading_loop.py`) has never accrued real
  elapsed time — its logic is proven with a mocked bar source in
  `tests/test_live/test_trading_loop.py`, but Phase 5's "≥2 weeks live"
  requirement needs actual market access and actual elapsed calendar time,
  neither of which this session has.
- This sandbox has no Docker daemon (`docker build` fails with "cannot
  connect to the Docker daemon"), so neither Dockerfile could be verified
  locally — but `bot/Dockerfile` WAS verified via a real Railway build (see
  the section below), which caught and led to fixing a real bug
  (`dashboard/` wasn't being copied in). `Dockerfile.dashboard` shares the
  same fixed package list and was sanity-checked the same way locally, but
  has not itself been through a real build.

## Railway investigation: a real, working alternative path — and a real bug it caught

After confirming the sandbox block, the same question was tested against
real infrastructure: a new Railway project
(`crypto-trading-bot-data-fetch`) was created and a service deployed
straight from this repo's `bot/` directory (branch
`claude/crypto-trading-bot-wz0pyf`), with a diagnostic start command
pinging both exchanges.

**First deploy failed the BUILD, not the network check** — and this was a
real bug, not an environment limitation: `pyproject.toml` declares
`dashboard` as an installable package (needed for `Dockerfile.dashboard`),
but `bot/Dockerfile` never copied the `dashboard/` directory in, so
`pip install .` failed there with `package directory 'dashboard' does not
exist`. This sandbox has no Docker daemon, so `docker build` had never
been run locally — Railway's build is what caught it. Fixed by adding
`COPY dashboard ./dashboard` to `bot/Dockerfile`, verified by simulating
the exact Dockerfile `COPY` set in a clean venv (`pip install .` now
succeeds), and confirmed for real by a green Railway build.

**Once it built, the network diagnostic gave a real, mixed result** from
Railway's `us-west2` region:

| Exchange | Result |
|---|---|
| `api.binance.com` | **HTTP 451** — Binance geo-blocks US-region IPs by policy; this is Binance's own restriction, not a network/proxy problem |
| `api.bitvavo.com` | **HTTP 200** — fully reachable |

So Bitvavo (this project's execution/paper-trading target) is reachable
from ordinary cloud infrastructure right now — the blocker really is
specific to this sandbox's egress policy, not to "no environment can reach
these exchanges." A non-US Railway region would plausibly unblock Binance
too (untested — the user redirected effort elsewhere before this was
tried; a European region is the next thing to attempt if deep Binance
history is still wanted).

At the user's direction, the Railway data-fetch effort was paused there
rather than actually pulling real Bitvavo OHLCV back into this repo — the
user plans to integrate CoinGecko themselves later instead. To support
that, `data/fetch_coingecko.py` was added: a tested (8 tests, mocked HTTP
via `responses`) CoinGecko fetcher returning the same
`[timestamp, open, high, low, close, volume]` shape as the Binance/Bitvavo
fetchers, ready to wire into `scripts/run_phase1_fetch.py` whenever
needed. Note: `api.coingecko.com` was independently confirmed blocked from
this sandbox too (`curl` and the `WebFetch` tool both got
`EGRESS_BLOCKED`/403) — the same sandbox-egress limitation applies to it,
same as Binance and Bitvavo; only the Railway path was shown to bypass it.

## What would produce a real result

In order, from an environment with network access to Binance and Bitvavo:

1. `python scripts/run_phase1_fetch.py` — fetches BTC/USDT, ETH/USDT (3yr,
   1h+4h) from Binance and BTC/EUR, ETH/EUR (90d) from Bitvavo, validates,
   stores as Parquet, writes `config/holdout.yaml`.
2. `python scripts/run_optimization.py --family trend_filtered_pullback
   --timeframe 1h` (repeat per family × timeframe) — runs the real
   50-config sweep, logs every run to `EXPERIMENTS.md` untagged (or tagged
   `[REAL:...]`), applies the walk-forward + overfit-rejection rules for
   real.
3. For any candidate that clears every gate on validation + walk-forward
   evidence: `python scripts/run_final_evaluation.py` — the ONE holdout
   run. Whatever comes out is final.
4. If (and only if) a strategy clears holdout too: `python
   scripts/run_paper_trading.py`, left running for ≥2 weeks, comparing
   realised vs. backtest-expected win rate/expectancy per Phase 5.
5. Update `RESULTS.md` with the real outcome, or extend this document if
   nothing clears every gate — per `RESEARCH.md §1`, that is a live
   possibility even with real data, not a symptom of anything having gone
   wrong.

## Why RESEARCH.md already expects this might not pass even with real data

Independent of the network blocker, `RESEARCH.md §1` lays out a real
tension in the Definition of Done: win rate ≥55% **and** profit factor
≥1.3 **and** beating buy-and-hold on a risk-adjusted basis simultaneously is
uncommon. Classic trend-following clears profit factor/R:R but rarely
clears win rate; classic mean-reversion clears win rate but usually fails
profit factor or drawdown once real costs are included. The three
strategies built here are deliberately hybridized (trend/regime filter +
defined-R:R trigger) specifically to try to sit in the achievable middle —
but there is no guarantee that middle is reachable on a 2-pair, 2-timeframe,
3-year dataset with a 200-trade minimum. A well-documented "no" on real
data would be exactly as legitimate an outcome of Phase 4 as a "yes" —
this document exists because the *sandbox* said no first, before the
*data* got a chance to.
