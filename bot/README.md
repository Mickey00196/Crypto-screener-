# Crypto Trading Bot

An autonomous crypto trading bot: research → data → backtest engine →
strategies → risk management → anti-overfit optimization → holdout
evaluation → paper trading → dashboard. Built per a detailed build brief
whose hard rules (no live trading by default, no lookahead, every backtest
includes costs, holdout touched once, report honestly) are enforced in
code, not just in prose — see [Hard rules, enforced](#hard-rules-enforced)
below.

**Read `FINDINGS.md` first.** This sandbox's network cannot reach any
exchange API, so no real backtest results exist yet — everything here is
built and tested, but Phase 1's data fetch and everything downstream of it
have not run against real data. `RESULTS.md` explains what did run (a
synthetic pipeline correctness check) and what a real run will produce.

## Architecture

```
bot/
  config/       settings.yaml (pairs, timeframes, costs, risk defaults) +
                holdout.yaml (generated by data/splits.py — not committed,
                see holdout.yaml.template)
  guard/        holdout_guard.py — runtime enforcement of "holdout touched once"
  data/         ccxt fetchers, validation, chronological splitting, Parquet
                storage, synthetic-data generator (pipeline smoke-testing only)
  engine/       event-driven bar-by-bar backtester: costs, portfolio,
                metrics, lookahead detector
  indicators/   trend/momentum/volatility/volume/structure/pattern/
                crypto-specific indicators, multi-timeframe alignment
  strategies/   the Strategy protocol + the 3 chosen strategy families
  risk/         position sizing, stops, daily loss limit, drawdown kill switch
                — deliberately separate from strategies/
  evaluation/   Definition-of-Done gates, walk-forward/purged-k-fold,
                final_evaluation.py (the only holdout reader)
  optimization/ bounded seeded config sampler, train/val optimization loop
  live/         paper broker (simulated fills), gated live broker, the
                trading loop, restart-safe state
  dashboard/    Streamlit: equity curve, drawdown, trade log, positions
  scripts/      CLI entrypoints for every phase above
  tests/        170 tests, mirrors the structure above
```

## Hard rules, enforced

- **No live trading by default.** `TRADING_MODE` defaults to `paper`
  everywhere (`settings.yaml`, `.env.example`). `live/live_broker.py`
  raises `LiveTradingDisabledError` on every order attempt unless
  `TRADING_MODE=live` AND real exchange credentials are present —
  `tests/test_live/test_live_broker.py` proves both failure modes and the
  one success path.
- **No lookahead.** `engine/backtester.py` computes a strategy's signal
  from data through bar *t*'s close, then fills the resulting order at bar
  *t+1*'s open — never *t*'s own close or *t+1*'s close/high/low.
  `engine/lookahead_check.py` proves this per-strategy by comparing signals
  computed on the full dataframe vs. a truncated one; it's checked against
  all 3 chosen strategies AND against a deliberately-broken strategy
  (`tests/test_engine/test_lookahead_detector.py`), which it correctly
  catches.
- **Every backtest includes costs.** `engine/costs.py`'s `CostModel` (fees
  + slippage, funding-cost hook for future perpetuals) is a required
  constructor argument of `Backtester` — there's no code path that skips it.
- **Holdout touched once.** `guard/holdout_guard.py` enforces this two ways:
  a caller-identity check (only `evaluation/final_evaluation.py` may
  request the "holdout" split) and a data-boundary check (any dataframe
  reaching past the holdout boundary is rejected unless explicitly passed
  with `allow_holdout=True`, which only `final_evaluation.py` does).
  `tests/test_guard/test_holdout_guard.py` proves a rogue caller is
  rejected AND that the legitimate caller succeeds.
- **Report honestly.** See `FINDINGS.md` and `RESULTS.md` — no result is
  reported that wasn't actually produced by running the code.

## What the strategies actually do (plain English)

All three combine a **trend/regime filter** with a **defined-risk trigger**
— none is a naive "RSI below 30, buy" system. Per `RESEARCH.md`, that
combination exists because pure trend-following clears risk:reward but
rarely clears the 55% win-rate bar, and naive mean-reversion clears win
rate but usually fails on drawdown/profit-factor once real costs are
included — so all three try to sit in the achievable middle.

1. **Trend-filtered pullback** (`trend_filtered_pullback.py`, primary
   pick). *"Buy temporary weakness in a confirmed uptrend."* Only looks for
   long entries when price is above a 200-period EMA and ADX confirms a
   real trend (not chop); within that filter, it waits for RSI to dip
   (a pullback) before entering, and exits once RSI recovers or the trend
   filter breaks. The stop and target are set from current ATR (volatility),
   not a fixed percentage.
2. **Volatility breakout with trend confirmation**
   (`volatility_breakout_trend.py`). *"Trade breakouts, but only the ones
   already moving with the trend, on real volume."* Enters when price
   breaks the prior N-bar high/low AND Supertrend already agrees with that
   direction AND OBV confirms the move isn't on thin volume; holds until
   Supertrend flips. (Simplification: uses the same fixed ATR stop/target
   as the other two families rather than the trailing/partial-profit exit
   `RESEARCH.md` describes — see `FINDINGS.md`/the strategy's own docstring
   for why.)
3. **Trend-continuation confluence**
   (`trend_continuation_confluence.py`). *"Follow the trend, but don't
   chase — buy the dip within it."* EMA cross sets direction, MACD
   histogram confirms momentum agrees, and a shallow RSI pullback (much
   closer to 50 than Family 1's deep oversold trigger) times the entry so
   it isn't bought at the top of a breakout candle.

Risk management (position sizing, stop/target distance, daily loss limit,
drawdown kill switch) lives entirely in `risk/risk_manager.py` — strategies
only ever say "long / flat / short."

## Config-driven, no hardcoded parameters

Every pair, timeframe, fee/slippage assumption, and risk default lives in
`config/settings.yaml`, loaded via typed `pydantic` models in `settings.py`.
Strategy hyperparameters are swept via `optimization/grid.py`'s seeded
sampler, never hand-picked into the code.

## Running each phase

```bash
# Real data fetch — needs network access this sandbox doesn't have (see FINDINGS.md)
python scripts/run_phase1_fetch.py

# A single backtest
python scripts/run_backtest.py --strategy-name trend_filtered_pullback --symbol BTC/USDT --timeframe 1h --split train

# The real 50-config optimization sweep for one family/timeframe
python scripts/run_optimization.py --family trend_filtered_pullback --timeframe 1h

# The one-shot holdout evaluation (only after a candidate clears every validation gate)
python scripts/run_final_evaluation.py --family trend_filtered_pullback --symbol BTC/USDT --timeframe 1h

# Paper trading (TRADING_MODE=paper by default; needs live market data)
python scripts/run_paper_trading.py --family trend_filtered_pullback --symbol BTC/EUR --timeframe 1h

# The synthetic pipeline smoke test (the one thing that DID run this session)
python scripts/run_pipeline_smoketest.py

# Dashboard
streamlit run dashboard/app.py
```

real bug (`dashboard/` wasn't being copied in — see `FINDINGS.md`).
`Dockerfile.dashboard` shares the same fixed package list but hasn't
itself been through a real build; verify before relying on it. Deploy as
two separate Railway services from this `bot/` subdirectory, with
`TRADING_MODE=paper` set (or left unset — it's the default) until you
deliberately decide otherwise.

## Extending to the full brief's scope

This pass covers BTC/USDT + ETH/USDT (Binance, research) and BTC/EUR +
ETH/EUR (Bitvavo, execution/paper) at 1h/4h. The full brief wants 5 pairs
at 5m/15m/1h/4h. To extend: add symbols/timeframes to
`config/settings.yaml`'s `pairs`/`timeframes` lists, re-run
`run_phase1_fetch.py`, and the rest of the pipeline (engine, indicators,
strategies, optimization, evaluation) needs no changes — it's already
parameterized over symbol/timeframe.

`data/fetch_coingecko.py` is a tested, ready-to-use alternative/
supplementary research-data source (no API key needed) — not currently
wired into `run_phase1_fetch.py`'s default flow. It returns true OHLC
candles with no volume from CoinGecko's `/ohlc` endpoint, backfilled with a
volume column from `/market_chart` via nearest-timestamp matching; note
CoinGecko's free tier coarsens candle granularity beyond ~90 days of
lookback, so it's a reasonable Bitvavo/Binance supplement rather than a
full deep-history replacement. See `FINDINGS.md` for why it hasn't been
exercised against the live API yet.
